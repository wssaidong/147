## 一、产品概述

### 1.1 产品定位

面向台球联盟管理者，提供一站式台球厅、助教、比赛的数字化管理工具。  
**核心差异**：专注联盟级统筹管理，而非单店运营。

### 1.2 目标用户

| 用户角色 | 使用场景 | 核心诉求 | 痛点 |
|----------|----------|----------|------|
| 联盟管理员 | 办公室 + 现场 | 全局掌控、数据分析、跨球厅协调 | 多球厅数据分散无法统一查看 |
| 球厅管理员 | 球厅现场 | 日常运营、比赛执行、球员管理 | 赛事组织效率低、成绩统计麻烦 |
| 裁判/记录员 | 比赛现场 | 快速录入成绩、查看赛程 | 纸质记录易出错、查找不方便 |
| 选手/助教 | 比赛前后 | 报名参赛、查看成绩、积分排行 | 赛果通知不及时、排名不透明 |

### 1.3 产品目标

1. 实现台球厅、助教、比赛的统一数字化管理
2. 支持办公室管理 + 比赛现场移动端使用
3. 提供数据报表辅助决策
4. **增强目标**：建立选手积分体系，形成联盟级赛事生态

## 二、市场与用户研究（头脑风暴 Round 1）

### 2.1 市场机会

- **行业趋势**：台球运动在中国持续升温，2024-2025年多地兴起"台球热"
- **市场空白**：现有产品多为单店管理工具，缺乏联盟级统筹方案
- **政策支持**：体育产业数字化转型受政策鼓励

### 2.2 用户调研洞察

| 场景 | 用户行为 | 痛点 | 机会 |
|------|----------|------|------|
| 赛前组织 | 人工统计报名、手动排对阵 | 效率低、易出错 | 自动生成赛程、一键通知 |
| 赛中执行 | 纸质记分、口口相传成绩 | 观众无法实时看到排名 | 实时排名大屏、直播式展示 |
| 赛后归档 | Excel存档或纸质存档 | 数据分散无法分析 | 历史数据沉淀、数据洞察 |
| 跨球厅协调 | 微信群沟通、信息碎片化 | 信息遗漏、责任不清 | 统一协作平台、操作日志追溯 |

### 2.3 关键假设

1. 联盟管理员需要同时管理 5-20 家球厅
2. 比赛频率：每月中型比赛 2-4 场，大型比赛 1 场
3. 用户愿意为高效的赛事管理付费

## 三、竞品分析（头脑风暴 Round 2）

### 3.1 竞品对比

| 竞品 | 定位 | 优势 | 劣势 | 借鉴 |
|------|------|------|------|------|
| 约球吧 | C端约球平台 | 用户量大 | 缺乏管理功能 | 约球体验 |
| 某球厅管理系统 | 单店管理 | 功能完善 | 不支持联盟视角 | 功能细节 |
| 围棋赛事平台 | 专业赛事 | 赛制专业、排名系统 | 界面复杂 | 赛程展示、积分体系 |
| 乒乓球赛事系统 | 赛事管理 | 操作流畅 | 非台球行业 | 裁判录入体验 |

### 3.2 差异化策略

1. **联盟视角**：多球厅统一管理，跨球厅数据汇总
2. **轻量级**：比专业围棋赛事系统更简单易上手
3. **移动优先**：比赛现场用手机即可完成所有操作
4. **社交元素**：选手间可互动，形成台球社群

## 五、用户场景与流程（头脑风暴 Round 4）

### 5.1 核心场景

#### 场景1：月度联赛组织

```
背景：联盟每月举办一次月度赛，约50人参赛
流程：
1. 管理员在后台创建比赛，填写基本信息，选择"单败淘汰制"
2. 设置报名截止时间，发布报名链接
3. 球员通过手机端报名，填写个人信息
4. 报名截止后，系统自动生成对阵图
5. 比赛当日，裁判使用移动端录入成绩
6. 每轮结束后，系统自动更新实时排名
7. 比赛结束，自动生成冠军海报和数据报告
8. 系统自动给获奖者增加积分
```

#### 场景2：跨球厅邀请赛

```
背景：联盟内3家球厅联合举办邀请赛
流程：
1. 发起球厅创建比赛，添加联合主办球厅
2. 各球厅分别组织报名，汇总到联盟
3. 赛程安排考虑各球厅场地时间
4. 比赛期间实现跨球厅成绩汇总
5. 最终在主赛场进行决赛
```

#### 场景3：裁判现场执裁

```
背景：淘汰赛第二轮，裁判使用手机录入成绩
流程：
1. 裁判打开比赛详情页，查看当前场次对阵
2. 点击"录入成绩"，输入局分（如 3:2）
3. 确认提交，系统自动更新赛程
4. 下一场对阵自动显示在屏幕上
5. 如有争议，裁判可标记"待审核"
```

### 5.2 异常流程

| 场景 | 处理方式 |
|------|----------|
| 球员临时退赛 | 标记退赛，对手直接晋级 |
| 比赛中断 | 保存当前状态，可暂停/恢复 |
| 成绩录入错误 | 管理员可修改，需填写原因 |
| 多人同分（循环赛） | 按胜率/净胜局/对战成绩依次判断 |

## 六、技术与实现考量（头脑风暴 Round 5）

### 6.1 技术选型建议

| 模块 | 技术方案 | 说明 |
|------|----------|------|
| 前端 | 响应式Web + 移动端H5 | 兼容手机和PC |
| 后端 | Node.js/Go + REST API | 轻量级、高并发 |
| 数据库 | PostgreSQL | 关系型数据，支持复杂查询 |
| 实时更新 | WebSocket | 比赛成绩实时推送 |
| 文件存储 | 对象存储（OSS/COS） | 比赛照片、视频存储 |

### 6.2 性能要求

| 指标 | 要求 |
|------|------|
| 页面加载 | < 2秒 |
| 成绩录入响应 | < 500ms |
| 实时更新延迟 | < 1秒 |
| 并发支持 | 支持100人同时操作 |

### 6.3 数据安全

- 操作日志完整记录
- 敏感数据（手机号）脱敏展示
- 权限控制到按钮级别
- 数据定期备份

### 6.4 扩展性预留

- 后续支持直播功能
- 接入支付系统（报名费、奖金发放）
- 与其他体育系统数据互通

## 七、非功能需求

### 7.1 响应式设计

- 桌面端：后台管理、办公室场景，全功能
- 移动端：比赛现场成绩录入、报名管理，简洁高效

### 7.2 权限控制

- 联盟管理员：全局数据访问
- 球厅管理员：仅本球厅数据
- 裁判：仅比赛执裁功能
- 选手：报名和查看自己数据

### 7.3 国际化预留

- 支持中英文界面切换
- 赛制规则可配置化
